QiPAI Store (`qipai-store`)

The `qipai-store` module provides persistent storage and retrieval capabilities for quantum states (`QTensor` objects) within the QiPAI framework. It aims for efficiency and is designed to handle the specific needs of storing complex amplitudes, entanglement information, and associated metadata.

Module Structure

The store is organized into several submodules:

  • `format/`: Defines the binary serialization format for states and related data.
    • qstate.bin.js: Handles encoding/decoding of the primary state binary format.
    • qindex.js: Manages index structures for container files.
    • qmeta.js: Encodes/decodes state metadata (using JSON initially).
  • `engine/`: Contains low-level reading, writing, and compression logic.
    • reader.js: Low-level binary reader (potentially stream-based).
    • writer.js: Low-level binary writer.
    • compressor.js: Optional compression algorithms (RLE, Gzip, etc.).
  • `fs/`: Implements different filesystem storage strategies.
    • flatfile.js: One state per file strategy.
    • container.js: Multiple states within a single indexed file.
    • dirmapper.js: Organizes flat files into directories based on IDs/metadata.
  • `query-engine/`: Provides the logic for querying the stored states.
    • queryBuilder.js: Defines the chainable Functional Query API.
  • `index.js`: The main public API entry point for the module.

Binary Format (`qstate.bin`)

The core storage format is designed to be compact and efficient:

HEADER (fixed size)
- Magic number (e.g., 4 bytes)
- Version (e.g., 1 byte)
- Num Qubits (e.g., 2 bytes)
- Sparse Count (Number of non-zero amplitudes) (e.g., 4 bytes)
- Entanglement Group Count (e.g., 2 bytes)
- Metadata Length (e.g., 2 bytes)

BODY
- Sparse amplitudes: [index (uint16), real (float32), imag (float32)] × Sparse Count
- Entanglement groups: [[q1_idx, q2_idx, ...], [qA_idx, qB_idx, ...], ...] (Encoded efficiently)
- Metadata: UTF-8 JSON blob (or potentially MsgPack)

This format prioritizes fast access to amplitude data and supports sparse states common in quantum simulations.

Storage Strategies

The store supports multiple ways to organize data on disk via the strategy option in saveState and loadState:

  • `flatfile`: Simple, one .qstate.bin file per quantum state. Requires a full file path.
  • `container`: Efficient for many states. Stores multiple states in one large file with an internal index. Requires a container file path and a unique stateId for each state.
  • `dirmapper`: Uses flat files but organizes them into directories based on stateId or metadata. Requires a base directory path and a stateId.

Functional Query API

The primary way to interact with stored states beyond simple load/save is the Functional Query API, accessed via the query() method exported by `qipai-store/index.js`.

query(options)

Creates a new QueryBuilder instance.

  • options.storageOptions: (Required) Object specifying the storage access details (e.g., { strategy: 'dirmapper', path: './my_states' }).
// Get a query builder for states stored in './data/run1' using dirmapper
const qb = qStore.query({ storageOptions: { strategy: 'dirmapper', path: './data/run1' } });

QueryBuilder Methods

The QueryBuilder provides chainable methods for filtering, acting upon, and retrieving states.

Filtering Methods

.whereMetadata({ key: value, ... }): Filters based on metadata fields.
.wherePhaseNear(targetPhase, tolerance?): Filters states based on quantum phase characteristics (requires loading state).
.whereAmplitudeAbove(threshold, qubitIndices?): Filters states based on amplitude magnitudes (requires loading state).
.entangledWith(qubitIndexOrGroup): Filters states where specific qubits are entangled (requires loading state).

Action Methods (Applied after filtering)

.entangle(target): (Conceptual) Apply entanglement operation.
.interfere(otherState, options?): (Conceptual) Perform interference with another state.
.measure(basis?, targetQubits?): (Conceptual) Simulate measurement on retrieved states.
.collapse(): (Conceptual) Collapse state according to previous measurement action.

Execution Methods

.limit(count): Limits the number of results.
.sort(field, direction?): Sorts results (likely based on metadata).
.listIds(): Executes query to return only matching state IDs (potentially faster).
.run(): Executes the full query, loads states, applies filters/actions, and returns resulting QTensor objects.
.output(): Executes the query and returns the result of the final action (e.g., measurement outcome).

Example

import * as qStore from './qipai-store/index.js';

async function findStates() {
    const results = await qStore.query({ storageOptions: { strategy: 'dirmapper', path: './states/exp_C' } })
      .whereMetadata({ status: 'processed', type: 'memory' })
      .entangledWith(0) // Find states where qubit 0 is entangled
      .limit(5)
      .run(); // Execute and get QTensor objects

    console.log(`Found ${results.length} states.`);
    // Process results (array of QTensor objects)
}

Performance Optimizations for Large-Scale Quantum States

QiPAI-Store includes optimizations for handling large-scale quantum states (terabyte/petabyte level) through two key components:

Sparse Quantum Tensor Representation

The QTensorSparse class provides a memory-efficient representation for quantum states:

  • Map-based storage: Only non-zero amplitudes are stored, dramatically reducing memory usage
  • Efficient operations: Matrix operations optimized to compute only necessary elements
  • API compatibility: Same interface as regular QTensor, making it easy to use
  • Memory analysis tools: Utilities to analyze sparsity and compare memory usage
// Example: Creating a sparse tensor for a 30-qubit state
const sparseTensor = new QTensorSparse({
    numQubits: 30,
    nonzeroAmplitudes: new Map([
        [0, qMath.complex(0.7071, 0)],  // |0...0⟩
        [1073741823, qMath.complex(0.7071, 0)]  // |1...1⟩
    ])
});

// Memory comparison with dense representation (30 qubits = 2^30 amplitudes)
const memoryStats = sparseTensor.getMemoryComparison();
// Result: { sparse: 40 bytes, dense: 17179869184 bytes, savingsPercent: 99.9999998% }

Distributed Architecture for Massive Scale

For truly massive scale quantum state storage, QiPAI-Store includes a distributed architecture designed for terabyte/petabyte scale:

Key Components

  • Metadata Service: Distributed metadata database for efficient state lookups
  • State Store Manager: Sharded storage of quantum states across multiple nodes
  • Query Coordinator: Orchestrates distributed queries and parallel execution
  • Distributed QStore API: Client-facing interface with the same API as single-node

Design Principles

  • Separation of metadata and state data: For efficient querying
  • Horizontal scalability: Add more nodes as data grows
  • Consistent hashing: For balanced data distribution
  • Parallel processing: Leverage multiple nodes for faster queries
  • Adaptive compression: State-specific compression for storage efficiency
// Example: Creating a distributed store
const store = new DistributedQStore({
    metadata: {
        type: 'elasticsearch',
        endpoints: ['http://elasticsearch:9200']
    },
    stateStorage: {
        type: 's3',
        config: { bucket: 'quantum-states', region: 'us-west-2' },
        shardingFactor: 32
    }
});

// Usage mirrors the single-node API
await store.saveState(qTensor, 'large-state-001', { tag: 'simulation' });
const results = await store.query()
    .whereMetadata({ tag: 'simulation' })
    .limit(5)
    .run();

QiPAI-Store as a Standalone Database

QiPAI-Store has the architecture to function as a standalone quantum state database. A prototype server implementation exposes QQL operations through HTTP endpoints:

Server Implementation

The server (server.js) provides HTTP endpoints for:

  • GET /api/states: List all quantum states
  • POST /api/states: Create a new quantum state
  • GET /api/states/:id: Retrieve a specific quantum state
  • POST /api/qql: Execute QQL queries

Client Library

A JavaScript client (client.js) provides a simple interface:

const client = new QStoreClient();

// Create a new quantum state
await client.createState({
    id: 'bell_state_01',
    numQubits: 2,
    metadata: { name: 'Bell State |00⟩ + |11⟩' },
    amplitudes: {
        0: { re: 1/Math.sqrt(2), im: 0 },  // |00⟩
        3: { re: 1/Math.sqrt(2), im: 0 }   // |11⟩
    }
});

// Execute QQL
const result = await client.executeQQL({
    qql: `
        LOAD STATE s
        WHERE s.metadata.name = "Bell State |00⟩ + |11⟩"
        USING STORE { strategy: 'flatfile', path: '' }
        MEASURE s ON QUBITS [0]
        RETURN LAST_RESULT
    `
});

Path to a Full Database Solution

To evolve into a full-fledged database, the following enhancements would be needed:

  • Server-Client Architecture: Network transport, authentication, concurrent connections
  • ACID Transaction Support: Atomicity, consistency, isolation, durability
  • Administration Tools: CLI, monitoring, backup/restore
  • Query Optimization: Cost-based optimizer, execution plans, caching
  • Enhanced QQL: Complex WHERE clauses, joins, aggregations

Unique Value Proposition

As a specialized database, QiPAI-Store offers advantages not found in traditional databases:

  • Quantum-Aware Query Language: Native understanding of quantum operations
  • Optimized Storage: Purpose-built for quantum states and entanglement
  • Domain-Specific Operators: Interference, entanglement, measurement
  • Scale to TB/PB Level: For large-scale quantum simulation data

Application Example: Quantum Chemistry

A detailed example (example-quantum-chemistry.js) demonstrates how QiPAI-Store could serve as a specialized database for quantum chemistry applications:

  • Storing molecular quantum states (H₂, H₂O) with metadata
  • Querying states by molecule type
  • Calculating energy differences between states
  • Simulating measurements for orbital occupation analysis
  • Creating superposition states to analyze bond dynamics

Quantum Query Language (QQL - Conceptual DSL)

While the Functional API is the primary programmatic interface, a symbolic Domain Specific Language (DSL), QQL, is under development to provide a more declarative syntax for quantum operations on the store.

Status: A custom, dependency-free engine (tokenizer, parser, interpreter) has been created in qql-engine/. It currently supports the following commands:

  • LOAD STATE var WHERE metadata.key = "value" USING STORE { strategy: 'flatfile', path: '...' }: Loads a state from a flatfile, decodes it (including amplitudes/entanglement), filters by metadata, and stores it in a variable.
  • INTERFERE targetVar WITH sourceVarOrContextVar: Adds the state vectors of two variables (one can be from initial context), storing the (unnormalized) result in the target variable.
  • MEASURE stateVar [IN BASIS_X|BASIS_Y|BASIS_Z] ON QUBITS [idx1, idx2, ...]: Sequentially measures the specified qubits of a loaded state in the specified basis. Collapses the state stored in the variable after each measurement and returns an array of outcomes (e.g., `[0, 1]`).
    • X-basis: Hadamard gates are applied before Z-measurement
    • Y-basis: S† and Hadamard gates are applied before Z-measurement
    • Z-basis: Direct computational basis measurement
  • ENTANGLE targetVar WITH (stateVar | "symbol"): Conceptually marks the target state variable as entangled with another state variable or a symbol (looked up/created via SymbolicMemory provided in context). Updates internal metadata.
  • RETURN stateVar | LAST_RESULT | COLLAPSE stateVar: Specifies the final return value of the script execution. Can be a state variable (returns the `QTensor`), `LAST_RESULT` (returns the value produced by the preceding command, e.g., the outcome array from `MEASURE`), or `COLLAPSE stateVar` (returns the state variable, which will hold the collapsed state after a `MEASURE`).

Other features (more complex WHERE clauses, specific qubit entanglement, other storage strategies for LOAD, etc.) are pending implementation.

Supported Syntax Examples

-- Example 1: Basic operations with Z-basis measurement

-- Load state 's' tagged "apple"
LOAD STATE s
WHERE s.metadata.tag = "apple"
USING STORE { strategy: 'flatfile', path: './data/apple.qstate.bin' }

-- Assume 'input_state' is passed in context
-- Interfere input_state into s (s = s + input_state)
INTERFERE s WITH input_state

-- Entangle s with the symbolic concept "fruit"
-- (Requires SymbolicMemory in interpreter context)
ENTANGLE s WITH "fruit"

-- Measure qubits 0 and 1 of the resulting state s (Z-basis)
MEASURE s ON QUBITS [0, 1]

-- Return the measurement outcomes (e.g., [0, 1] or [1, 0] etc.)
RETURN LAST_RESULT

-- Alternatively, to return the final collapsed state:
-- RETURN s

-- Example 2: With X-basis measurement and collapsed state return

-- Load state 's' tagged "apple"
LOAD STATE s
WHERE s.metadata.tag = "apple"
USING STORE { strategy: 'flatfile', path: './data/apple.qstate.bin' }

-- Entangle with symbolic concept
ENTANGLE s WITH "fruit"

-- Interfere with input state from context
INTERFERE s WITH input_state 

-- Measure in X-basis (applies Hadamard gates before Z-measurement)
MEASURE s IN BASIS_X ON QUBITS [0, 1]

-- Return the collapsed state after measurement
RETURN COLLAPSE s

This QQL would aim to abstract the quantum operations into a more human-readable format, potentially useful for configuration files or higher-level tooling.
